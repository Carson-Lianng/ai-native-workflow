# 03 · 门禁：DoD、AC 与反证

门禁的目的不是"看起来规范"，而是**让没参与讨论的人也敢相信这条任务真的做完了**。

## 一、三层结构

| 层 | 承载物 | 作用 |
|---|---|---|
| 规则 | `definition_of_done`（项目级默认 + 每任务 `--dod`） | 说明什么算完成 |
| 检查 | `--ac` 验收断言 + `--check-ac` 逐条勾选 | 把完成变成可执行判断 |
| 门禁 | 未全勾不转 `Done` | 让检查有后果 |

三者缺一不可：只有规则没有检查 = 口号；只有检查没有门禁 = 建议。

## 二、项目级 DoD

写在 `backlog/config.yml`（**注意是 `backlog/config.yml`，不是仓库根目录**）：

```yaml
definition_of_done:
  - 测试通过且无回归
  - 所有验收断言已逐条 --check-ac 标记完成
  - 五轴审查通过（正确性/设计/安全/测试/体验）
  - 决定与文档已更新（backlog decision / docs）
  - 关键检查已做反证
```

轻量模式精简为 3 项：测试通过 / AC 全勾 / 决定与文档已更新。

单条任务需要额外要求时：

```bash
backlog task create "迁移用户表" --dod "回滚脚本已演练" --dod "迁移耗时 < 5 分钟"
```

## 三、AC 写法：可证伪

| 不合格 | 合格 |
|---|---|
| 权限功能正常 | 无权限用户提交被 403 拒绝 |
| 性能达标 | 1000 条数据下列表首屏 < 1s |
| 错误处理完善 | 数据库超时时返回 503 并记录 error 日志 |
| 支持导出 | 导出 10 万行 CSV 不 OOM，字段与页面一致 |

判据：**换一个不了解上下文的人，能不能只凭这条断言判断通过与否。** 不能，就重写。

## 四、labels 承载门禁流转

`labels` 不是装饰，是状态机的旁路：

| 标签 | 含义 |
|---|---|
| `needs-review` | 已实现，待审查 |
| `reviewed` | 审查通过 |
| `needs-test` / `tested` | 待验证 / 已验证 |
| `blocked` | 缺凭据、等外部条件、需人决策 |

```bash
backlog task edit TASK-1 --add-label needs-review
backlog task edit TASK-1 --add-label reviewed --remove-label needs-review
```

> 追加标签用 `--add-label`。`-l` 是**替换全部标签**，会把里程碑、模块标签一起清掉。

## 五、反证纪律

只看绿色退出码、全勾、CI 通过，**不足以**证明门禁可信——检查本身也可能是坏的（跑 0 个测试也算通过）。

每个关键检查做一次反证，三条都满足才算可信：

1. **已知正确输入 → 通过**
2. **故意构造一个目标缺陷 → 因正确原因失败**（不是崩溃、不是超时，而是恰好指出该缺陷）
3. **恢复输入 → 再次通过**

典型做法：

```bash
# 1. 基线
npm test                      # 期望：全绿

# 2. 注入缺陷：把校验条件取反 / 删除一行鉴权 / 改错断言
npm test                      # 期望：恰好那条用例失败，且失败信息指向该缺陷
#    如果仍然全绿 → 这条用例没有真的在测东西

# 3. 恢复
git checkout -- <file> && npm test   # 期望：重新全绿
```

容易漏做反证的地方：权限校验、金额计算、幂等与并发、空值 / 边界、迁移脚本。

## 六、Blocked 的正确用法

缺凭据、等外部接口、需人拍板时——**停下来，不要无限重试**：

```bash
backlog task edit TASK-7 -s "Blocked"
backlog task edit TASK-7 --notes "等对方提供 sandbox 密钥（2026-11-02 前）"
```

`Blocked` 需先在 `backlog/config.yml` 的 `statuses` 中声明；不改状态列表时，用 `blocked` 标签 + `--notes` 记录原因。
